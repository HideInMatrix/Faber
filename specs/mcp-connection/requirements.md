# 第三方 MCP 接入与配置明文展示：需求审核稿

状态：用户已确认实施。本次随 Faber 1.9.0 提交发布。

## 1. 目标与范围

用户使用自己申请的服务密钥或自己的登录授权，将第三方 MCP 服务接入 Faber。Faber 获取工具列表并向 Agent 暴露工具，后续调用使用该服务对应的凭据。

主要使用过程：添加 MCP → 填写连接信息及认证方式 → 测试连接 → 保存 → 启动 Runtime → Agent 使用工具。

用户故事：

- 作为用户，我希望填写服务地址和自己的 API Key/Token 后即可连接，无需编写 Header JSON 或托管 CIMD 文档。
- 作为用户，我希望本地 MCP 可以直接填写程序、参数和环境变量，通过自己的凭据启动。
- 作为用户，我希望地址、密钥和已保存的配置值直接可见，便于核对、复制和修改。
- 作为用户，我希望连接失败时知道失败阶段和原因，而不是统一收到 Unauthorized 或 CIMD 配置提示。

本次包含：标准传输、常见凭据认证、标准 OAuth、配置交互、兼容迁移、连接诊断。

不包含：替用户申请密钥或处理账号权限、服务商专用签名/私有认证、替 Faber 申请厂商准入。服务端明确拒绝客户端时如实提示，不将厂商批准列为所有服务的前置步骤。

## 2. 接入方式

### R1. 远程 MCP：地址与用户凭据

普通表单提供名称、服务地址、传输和认证方式。连接 ID 自动生成，保留高级编辑入口。

| 认证方式 | 用户填写 | 预期行为 |
| --- | --- | --- |
| 无认证 | MCP 地址 | 直接连接 |
| Bearer Token | MCP 地址、自己的 Token | 自动构造 Authorization: Bearer … |
| API Key | MCP 地址、Header 名称及自己的密钥 | 按服务要求构造密钥请求头 |
| OAuth | MCP 地址；需要时补充客户端信息 | 发现服务端能力，打开浏览器完成授权 |

- 当用户选择 Bearer Token 或 API Key 时，Faber 应自动完成凭据传递，不要求用户填写 Header 引用 JSON、环境变量引用或 CIMD 文档。
- 当服务需要额外普通请求头时，Faber 应提供名称/值表格；已有 Header 引用和环境变量引用放在高级配置中继续兼容。
- 当用户填写自己的服务密钥时，Faber 应只在连接和调用对应服务时使用该凭据，不将它视为模型服务的 API Key。

### R2. 本地 MCP：程序与环境变量

- 当用户选择 stdio 时，Faber 应提供可执行程序、参数列表和环境变量名称/值表格。
- 当用户填写环境变量中的 API Key/Token 时，Faber 应将它传给对应子进程，不要求额外创建系统环境变量。
- 当用户打开已有参数 JSON 或环境变量引用配置时，Faber 应保留其语义；常用编辑不再强制手写 JSON。

### R3. 传输协议兼容

- 当服务使用 stdio 或 Streamable HTTP 时，Faber 应继续支持现有连接方式。
- 当服务使用旧版 HTTP + SSE 时，Faber 应提供明确的兼容连接选项。
- 当服务连接失败时，Faber 应区分传输不支持、地址/网络异常和认证失败，不通过修改认证方式掩盖传输问题。

## 3. 标准 OAuth

### R4. 取消 CIMD-only 限制

- 当用户选择 OAuth 时，Faber 应先发现受保护资源及授权服务器信息，不统一要求用户托管 CIMD 文档。
- 当用户已有该服务的预注册客户端信息时，Faber 应支持填写 Client ID、必要的 Client Secret、回调地址和授权范围。
- 当服务声明支持 CIMD 且有适用的客户端文档时，Faber 应支持 CIMD。
- 当服务支持并允许动态客户端注册时，Faber 应支持 DCR；存在注册端点不等于服务一定允许当前客户端注册。
- 当无法自动取得客户端身份时，Faber 应明确要求补充客户端信息，而不是重复提示填写 CIMD。
- 当服务采用 none、client_secret_basic 或 client_secret_post 时，Faber 应按双方支持的方式处理客户端认证，不再强制 none。
- 当授权成功、Token 到期、授权被取消或退出登录时，Faber 应分别正确保存/刷新/恢复/清除对应状态，保留 PKCE、state 和 issuer 绑定。

### R5. 服务端限制的处理

- 当服务端明确只接受 OAuth 时，Faber 应提示该要求，不把 API Key 与 OAuth Client Secret 混为一谈。
- 当服务端明确拒绝客户端注册或接入时，Faber 应显示对应阶段和服务端可用于诊断的信息；不得仅凭 401 就断定客户端未获准入。
- Figma 官方远程 MCP 作为“不接受个人 Token 且限制客户端接入”的兼容性提示案例，不作为 API Key 主流程的模板，也不承诺本次改造后必然可以直连。

## 4. 输入框统一明文展示

### R6. 无需显隐操作

本次统一范围：第三方 MCP 地址、API Key、Bearer Token、环境变量值、普通 Header 值、Client ID、Client Secret、CIMD 文档地址、OAuth 回调地址，以及 Runtime 配置中的网络令牌与 OAuth 密码。

- 当用户新增、编辑、保存或重新打开上述配置时，相关输入框应直接明文展示，不使用 password 类型、不显示星号，也不要求点击眼睛按钮才能查看。
- 当用户打开已保存的配置时，Faber 应回显实际保存的手填值，而不只显示“已配置”或一个空白替换框。
- 当用户关闭本机保存时，凭据按现有策略仅在当前应用进程中保留，不承诺进程退出后仍可回显。
- 当用户点击清除并保存时，Faber 应删除对应值；取消编辑不应改变原配置。保留明确的清除操作，避免未填替换值时意外删除已有凭据。
- 明文展示属于本机配置界面的行为；公共 MCP 工具、健康接口及运行日志不因此输出凭据。无需增加额外的显示确认或警告流程。

## 5. 测试、保存与连接状态

### R7. 操作流程

- 当用户点击“测试连接”时，Faber 应使用当前表单中的地址和凭据完成临时连接并列出工具，成功后显示工具数量和名称。
- 当用户只做连接测试时，Faber 不应强制先保存配置，不应执行业务工具、启动公网隧道或擅自重启 Runtime；测试结束应关闭临时连接。
- 当配置和凭据均保存成功时，Faber 才应提示保存成功；失败时保留草稿和已有值，明确指出失败，不提前提示成功。
- 当 Runtime 正在运行时，沿用现有停止后编辑的规则，界面明确提示，不在后台自动停止用户的 Runtime。
- 当服务处于未连接、连接中、待授权、已连接或失败状态时，列表应显示相应状态；已连接时显示工具数量，失败时提供具体原因和重试入口。
- 当用户调用第三方工具时，Faber 应保留完整原名，不恢复服务前缀、名称截断或哈希后缀；重名仍明确报错。

### R8. 失败提示

至少区分：输入配置缺失、地址/网络失败、传输协议不兼容、密钥认证被拒、OAuth 发现/注册/回调/Token 交换失败，以及工具发现失败。

服务商明确说明的限制应原意呈现；诊断信息不包含密钥或 Token 原值。

## 6. 审核后的验收范围

- 以隔离的 MCP 服务验证：无认证、Bearer Token、API Key、stdio 环境变量、Streamable HTTP 和旧版 SSE。
- 以隔离授权服务器验证：预注册客户端、CIMD、允许/拒绝 DCR、三种客户端认证方法、Token 刷新、授权取消及旧凭据迁移。
- 通过实际页面操作验证：常用接入无需 JSON、全部相关字段明文展示、保存后重新打开可回显、清除/取消语义、测试不强制保存、错误与重试。
- 不使用用户真实密钥、不执行业务工具、不申请服务商准入；自动化测试及结果仍只保存在本地，不纳入 Git 跟踪。

用户已确认实施；实现设计、实施任务与验收结果分别记录于 design.md 和 tasks.md。
